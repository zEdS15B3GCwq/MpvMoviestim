## Plan: Override unsupported PsychoPy parent members in `MpvMoviestim`

The overrides split into three groups: unsupported members, supported members that need mapping or change notification, and members to leave alone.

### Can blit support rotation and opacity?
Not with `glBlitFramebuffer`. It only copies and scales, with no blending and no transform. Both are possible if `draw()` instead drew a textured quad from the intermediate texture with a small shader (alpha, rotation matrix). That is a different draw path, so I treat them as unsupported here.

### Group A: unsupported (warn, ignore, return a default)

| Member | Source | Getter default | Notes |
|---|---|---|---|
| `opacity` (property) | `BaseVisualStim` | `1.0` | The parent returns `1` when unset. |
| `ori` (`attributeSetter`) | `BaseVisualStim` | `0.0` | Never call super. `_rotationMatrix` then stays identity, so `verticesPix` stays axis-aligned and is a valid bounding rect. |
| `alphaThreshold` (`attributeSetter`) | `BaseVisualStim` | `0.0` | Default taken from its docstring. |
| `vertices` (setter only) | `WindowMixin` | Delegate quietly to the parent getter | `_updateVertices` reads this getter internally, so a warning there would spam. Arbitrary shapes can't be blitted. |
| `setOri`, `setOpacity`, `setAlphaThreshold` | `BaseVisualStim` | n/a | `setAttribute` reads the getter first (and `setOpacity('+')` does `self.opacity += ...`), so each call would warn twice. Override them to warn once. |

`updateOpacity()` is already a no-op, so it needs nothing.

### Group B: supported, but needs an override

1. **`flip`, `flipHoriz`, `flipVert`** (`WindowMixin`):
   - Map them to the existing `flip_horizontal` and `flip_vertical` fields, which blit already supports.
   - Don't call super, which would create `_vertices` and set `_flip`.
   - The `flip` getter must return a `(1, 2)` bool array. `vertices` and `_updateVertices` pass it into `Vertices`, which asserts that dtype.

2. **`anchor`** (`WindowMixin`):
   - Call super, then set `_needVertexUpdate = True` and notify MMS.
   - PsychoPy's setter updates `Vertices.anchor` but never sets the dirty flag, so `verticesPix` goes stale.
3. **`pos` and `size`** (`WindowMixin`, via `BaseVisualStim`):

### Is the flag-and-override idea for question 2 necessary?
Not for performance, but it is still a good design.
- **Parent caching:** `Vector` stores `pix` and caches each unit conversion until it is set again. `verticesPix` recomputes only when `_needVertexUpdate` is `True`. Reading it per frame costs a property call, a flag check and a dict lookup. The numpy work (`Vertices.pix`) happens only on a change.
- **Why override anyway:**
  - Without it, MMS has no change notification. It would have to poll `_needVertexUpdate`, and `verticesPix` clears that flag when read.
  - You still need to derive and cache the integer rect once per change.
  - `anchor` needs the override regardless.
- **Recommended hooks:** `pos`, `size` and `anchor` setters. Don't hook `units`. Call super first, then read `verticesPix` once.

### Prerequisites in current MMS (clashes, not part of the overrides)
- MMS never calls `super().__init__(win, units, name, autoLog)`.
  - That single call initialises `MinimalStim`, `ContainerMixin` and the `win`, `units`, `_pos` and `_size` objects, because the `MinimalStim` init chain reaches `ContainerMixin.__init__`.
  - Until it is called, `win`, `autoLog`, `_pos`, `_size` and `_rotationMatrix` don't exist.
- `_size` (tuple or `None`), `_units`, and `_position` clash with the parent's `Size`/`Position` objects. `_updateVertices` reads `self._size` and `self._pos` as `Vector`s.
- MMS's own `size` property and setter must delegate to the parent instead of replacing it.
- `autoDraw` needs `self.depth` in the instance `__dict__`. `attributeSetter` has no `__get__`, so otherwise the descriptor object itself is returned. Set `depth` in init.
- With `autoDraw`, `Window.flip()` calls `draw()` every frame. MMS currently logs a warning each frame when it is not `PLAYING`.

### Question 3: record the render size per buffer (theoretical)
This is feasible and cheap. It is strictly necessary only if resizing during playback is supported, which the `size` setter docstring says it is.
- **Current race:** the worker reads `self._draw_rect[2]` and `[3]` in two separate loads, so it can see a torn width/height pair. The main thread blits using whatever `_draw_rect` is at that moment, which may not match what was rendered into that FBO. The result is a rescaled or partially stale blit for the frames around a resize.
- **Fix:** keep a per-FBO rendered size, e.g. a two-slot list in `ThreadedState`.
  - The worker snapshots `_draw_rect` once and records `(w, h)` for the target buffer before setting `buffer_flip_required` under `buffer_fbo_lock`. The existing lock and fence give the needed ordering.
  - The main thread blits the source region `(0, 0, rendered_w, rendered_h)` to a destination of the same size, so blit never scales.
  - The destination position comes from the current rect (re-centred for the rendered size), so position changes show up immediately without a re-render.
- **Gotcha:** after a size change, the new size appears only when the worker renders again. When MPV has no new vframe (paused, or a video frame rate below the display rate), nothing triggers it. You would need a resize-pending flag that sets `wakeup_worker_trigger` and makes the worker re-render the current frame even if `update()` returns `False`.
- **Non-threaded mode:** `_draw_direct` has the same stale-size issue, because it renders only when `update()` is true.
